## 4. B를 실제로 막는 잔여 문제

### 4-1. 관찰 화면이 유효 경계를 계속 보장하지 않음 — P1

`observeCamera()`의 box는 여전히 생존 시 `x±26`, `y−96…y+24`, 사망 시 별도 고정 상수다. `drawHeroUnit()`의 rig/프레임/코드 드로잉 분기에서 실제 외형 경계를 받지 않는다(`src/render/field.ts:745`, `:952`). 상수를 조금 키운 것만으로 머리장비·무기·자세별 실제 경계 요구를 충족할 수 없다.

**함수 재현:** 390×106, 선택 영웅 `(500,500)`에서 진입 카메라는 `(500,464,0.75)`, 대리 box 화면 y는 `[8,98]`로 개선됐다. 다음 프레임에 렌더 위치 `smooth.y=480`, `dt=16`을 주면 카메라 y는 약 `462.597`, box 상단은 **−5.948px**가 된다. 보간 뒤의 카메라를 유효 범위로 제한하지 않아 **자체 box 계약조차 깨진다**. 이 수치는 실제 머리 픽셀을 측정한 결과가 아니라 코드의 프레이밍 제약 위반 재현이다.

화면 밖 집계도 현재 카메라는 쓰지만 `smooth`가 아닌 원본 `h.x/y`와 또 다른 `10/80` 상수를 쓴다(`:776`). 카메라 `(500,464,0.75)`, 동료 원본 x=780·렌더 x=745에서 동료 box의 왼쪽은 화면 x=359.25로 390px 화면 안에 걸치는데도 **밖 1명**으로 센다. “완전히 밖”이라는 새 주석의 의미조차 맞지 않는다. 실제로 그리는 경계와 같은 좌표를 프레이밍·집계에 공유해야 한다.

퀵바는 `FieldView.tsx:114`에서 한 번 측정하지만 effect 의존성이 `[manage, closed]`뿐이다. `ResizeObserver`는 캔버스만 보고 `resize()`만 호출한다(`:90`). 사냥 상태를 유지한 채 화면/글자/퀵바 높이가 달라지면 `insetBottom`은 갱신되지 않는다. 진입 시 측정 PASS와 지속 측정 PASS는 구분해야 한다.

### 4-2. 기본 조작·작은 높이·글자 계약 미완료 — P1

**자동 접힘 계산이 실제 스크롤 높이와 다르다.** `FieldView.tsx:103`은 제목/선택/탭을 고정값으로 빼지만, 새로 모든 `Win`에 추가한 최소 36px `.page-info`를 빼지 않는다. safe-area 0, 성장, 높이 660px에서 계산상 `258px ≥ 240`라 띠를 펼치지만 실제 본문은 **222px**다. 390×600 화면에서 접혔다는 사실만으로 임계 높이 전체를 통과한 것은 아니다. 실제 본문/고정 행을 측정하고, 공간 회복 시 선호를 유지하는 동작까지 확인해야 한다.

제공 화면에서도 390×844의 본문은 명세상 442px에서 정보 행 36px을 뺀 **406px**, 360×800은 398px에서 **362px**로 줄었다. 대상 제목 복구 자체는 좋지만 추가 고정 행의 비용을 높이 계약에 반영해야 한다. 필요하면 대상·포인트를 명세대로 본문 첫 줄로 옮길 수 있다.

### 4-3. 사냥에서 직접 연 상세는 브라우저 Back 복귀점을 만들지 않음 — P2, 복귀 계약 차단

NPC의 관리 진입은 고쳤지만 `setModal/pushModal`은 history를 만들지 않는다(`src/ui/game.ts:262`). **함수 재현에서 사냥 상태→퀵슬롯 상세의 history push는 0회**다. 브라우저의 직전 문서가 외부 페이지인 상태라면 상세를 닫을 앱 소유 entry가 없어 Back으로 문서를 떠날 수 있다. 이는 실제 브라우저 이탈을 이번에 재현했다는 뜻이 아니라 history 진입점 부재를 확인한 것이다.

`popstate`는 관리 페이지가 있으면 `back(true)` 후 page entry를 다시 넣는 방식이다(`game.ts:103`). 관리 중의 단계 복귀 개선은 인정하되, 사냥 상세·오프라인 보고까지 동일하게 보장한다고 볼 수 없다. **모달 우선 처리라는 JavaScript 함수 순서와 브라우저가 앱 문서에 머무는 것은 다른 조건**이다. 실제 브라우저 Back으로 관리 상세와 사냥 상세를 모두 검사해야 한다.

### 4-4. 함께 닫아야 할 명시적 인수 잔여

다음은 위 P1과 같은 화면 파손을 새로 재현한 항목은 아니다. 그래도 R3의 필수 묶음에서 빠진 작업이므로 완료 또는 명시적 범위 재합의가 필요하다.

- 가방 카드 항목을 카드/슬롯 관리의 보유 목록으로 연결한다. 현재 별도 재고 화면은 그대로다.
- 모달 장착 대상의 원본을 안정된 영웅 ID로 바꾼다. inert로 배경 순서 변경 경로를 막았다는 사실과 데이터 계약 충족을 혼동하지 않는다.
- 선행 스킬을 `강타 현재 0 / 필요 5`처럼 표시한다. 다섯 상태의 라벨은 구현됐지만 사용자가 부족량을 판단하는 설명이 남았다.
- 실제 브라우저에서 포커스 trap/트리거 복귀, 부모 스크롤/필터, 판매·소비·카드 삽입의 단일 실행을 검수한다. 원래 요구한 390×844·360×800·500×900 전체 메뉴와 200%/320px 경계를 포함한다.

## 5. 21/21 자동 검사의 의미와 한계

자동 검사 추가는 유효하다. 주 메뉴 재클릭, 선택 ID 유지, 서비스/지도 Escape, 부모 영웅 선택 유지, 판매, 상세 X, 배지 분리, QA 저장값 비교가 실제 앱을 대상으로 연결돼 있다. 다만 21개 PASS를 다섯 묶음 전체의 인수로 치환할 수 없다.

- **브라우저 Back:** 실제 `history.back()` 후 단계 복귀를 단언하지 않고, NPC 진입 뒤 `history.state.mm`만 확인한다(`tools/ui-check.html:43`).
- **포커스·입력:** `inert` 속성만 검사한다(`:64`). `.click()`은 실제 pointerdown/up·키보드 탐색을 재현하지 않는다. 띠의 `.click()` 검사는 렌더러 pointerdown 차단의 직접 테스트가 아니다(`:78`).
- **스킬 5상태:** 상태 집합에 `+1`이 있고 나머지 값이 허용 목록에 들면 통과한다(`:87`). `+1` 하나만 있어도 통과하며, 다섯 상태 모두 존재하거나 각 조건에 맞는지 확인하지 않는다. 제공 스크린샷은 MAX/포인트 부족/선행 필요를 추가로 뒷받침하지만 학습 종료·학습 가능을 모두 증명하지는 않는다.
- **단일 실행:** 장비 한 건 판매만 검사하고 제니는 증가 여부만 본다(`:66`). 이는 유용한 회귀 검사지만 소비·삽입·빠른 반복 입력 전체의 보장은 아니다.
- **저장 분리:** 시작/끝 저장 문자열 일치를 확인한다(`:90`). 중간 쓰기 호출이 전혀 없었다는 계측은 아니다. 이번 QA 첫 저장은 별도의 쓰기 횟수 재현으로 보강했다.
- 카메라·실제 hit box·접힘 임계값·필터/스크롤 왕복·확대/다중 슬롯은 이 도구의 검사 대상이 아니다.

테스트를 늘릴 때는 위 누락된 동작을 검증해야 한다. 현재 PASS 문자열 수나 CSS 상수의 복제만 추가할 필요는 없다.

## 6. 차단하지 않는 개선과 최종 판단

세계 지도 그림의 최초 접힘/펼침, 전직 배지 점멸 정리, 사용하지 않는 `.sheet/.hero-tabs` 정리, 남은 옛 메뉴 안내 문구는 R3에서 허용한 후속 개선으로 유지한다. 이 때문에 B를 막는 것은 아니다.

`doing` 정확성·왼쪽 레일 정리·사냥/보스 정보·퀵바 빈 칸 접기와 명시적 편집·프리셋 차이·파티 힐/자동 스킬·스탯 실제 구매량과 추천안 미리보기는 [R2 §3](codex_r2.md)의 **B 범위**다. 그 기능이 아직 없다는 이유로 A를 FAIL 처리하지 않는다. 다만 퀵바의 안전한 독립 입력 영역은 이미 A의 필수 조건이다.

**최종 No-go 유지.** 우선 관찰 경계/추적과 최소 조작성/실제 높이 계산을 수정하고, 상세 browser Back 및 명시적 잔여 계약을 닫은 다음 브라우저 인수 증거를 보강해야 한다. 6탭·공통 셸을 다시 설계할 필요는 없고, 이번에 PASS로 확인한 수정도 되돌릴 필요가 없다. 현재는 B 착수 순서를 확정하는 승인 단계가 아니다.
