# Mini Midgard UX 독립 검토 — Round 1

작성: Codex · 2026-10-07 · 구현 전 토론안

**가장 먼저 바꿀 것은 파티 AI를 이해하고 조정하는 동선, 관리 화면의 공간 배분, 실제 휴대폰에서의 조작 크기다.** 지금은 사냥을 지켜보는 화면과 상세 설정 화면이 같은 공간을 나눠 쓰는데, 어느 쪽도 충분히 읽히지 않는다. RO의 재미인 직업 조합·특정 몬스터 사냥·슬롯 장비와 카드 선택을 전면에 놓는 개편을 제안한다.

## 검토 범위와 근거 표기

- 첨부된 10개 화면과 `shots/`의 대응 이미지, UI·관련 게임 코드를 대조했다. Claude의 독립 검토는 읽지 않았다.
- 좌표·크기는 별도 표기가 없으면 **CSS px**다. 이미지 1000×1800의 좌표를 2로 나눈 500×900 기준이며, 실제 앱 폭은 `src/styles.css:43`의 `max-width:480px` 때문에 좌우 10px 여백을 뺀 480px다.
- 스크린샷은 Lv 30 / Job 20 QA 시작 상태다. 몬스터가 없는 순간, 카드 0장, 장비 미착용, 경험치 0%를 일반 플레이의 빈도나 밸런스 결함으로 판단하지 않는다. 빈 상태에서 무엇을 안내하는지만 평가한다.
- 아래의 **관찰**은 화면 또는 코드 근거, **제안**은 아직 구현되지 않은 설계다. 동영상·실기기 조작·스크린리더·전투 반복 체감은 검증하지 않았다. 좁은 화면의 예상 문제도 관찰된 현상과 구분한다.
- 요청에 적힌 `src/ui/styles.css`의 실제 위치는 `src/styles.css`다. 코드 줄 번호는 최초 열람 시점 기준이다. 최종 확인 중 파티 역할 선택·AI 관련 별도 작업의 변경을 발견했다. 새 역할 선택과 프리셋의 역할 보존 추가는 확인했으나, 해당 변경의 전투 동작은 이번 정지 화면 검토에 포함하지 않는다. 이후 이동한 줄은 함수명으로 찾을 수 있다.
- [퀄리티 가이드](../../../RiftLoopPrototype/docs/퀄리티%20가이드.md)의 접수→준비→실행→접촉→결과→정착, 빈도별 강조, 보상 확정과 연출 분리 원칙을 적용했다. 다른 게임의 타격 시간·속도 수치를 가져오지는 않았다.
- 공수는 개발자 1인 기준 상대 크기다. **S**: 국소 UI·문구·스타일, **M**: 여러 화면의 상태·동선·공통 컴포넌트, **L**: 화면 구조 또는 저장·이벤트 계약 변경. 아래 공수는 중복되는 공통 작업 때문에 단순 합산하지 않는다.
- 와이어프레임의 `값`, `n`, `예`는 동작 설명용이다. 실제 수치·확률·제약은 게임 데이터에서 읽는다.

## 1. 플레이어 영향도 순 상위 15개 문제와 제안

### 1) 최우선 시스템인 파티 AI가 보조 메뉴에 있고, 하나의 작전이 세 화면으로 갈라져 있다

**화면:** 필드, 파티, 스킬, 퀵슬롯.

**관찰:** [party.png](shots/party.png)는 직업별 역할·작전·추격까지 보여주는 좋은 기반이다. 그러나 입구는 우상단 사람 아이콘이며, 하단 6개 탭에는 파티가 없다(`Hud.tsx:28,111`). 파티의 펼친 설정도 힐은 스킬, 포션은 퀵슬롯으로 안내한다(`Party.tsx:133–146`). 힐 기준은 스킬 목록 맨 아래다(`StatusSkills.tsx:233–239`). 프리셋은 전원의 개별 전술을 즉시 덮어쓴다(`Party.tsx:83–89`); 사용자 설정과의 변경 차이를 볼 수 없다.

**영향:** 힐러가 힐하지 않거나 마법사가 SP를 아끼는 상황에서 플레이어가 자신의 설정과 AI 판단을 연결하기 어렵다. 직업별 AI가 이 게임의 주력이라면 설정의 존재보다 **설정→실제 행동→결과**를 확인하는 경로가 우선이다.

**제안 — L:** 하단에 `파티`를 고정한다. 파티 화면을 `작전 / 파티원`으로 구성하고, 파티원 상세에서 공격 대상·위치·공격 스킬 정책·힐 기준·스킬 자동 사용을 함께 편집한다. 포션은 파티 공용임을 명시한 바로가기로 같은 퀵슬롯 설정을 연다. 설정 저장소는 기존 `tactics`, `auto`, `quick`을 공유한다. 스킬 화면에도 자동 사용 상태와 이 상세로 가는 링크를 남긴다.

- 작전 변경 전 `교전 3→1 / 쿠키 보호→협공 / 보리 추격 보통→리더 곁`처럼 **바뀌는 값만** 펼쳐 보여주고 `적용`한다. 같은 작전 재선택은 불필요한 덮어쓰기를 하지 않는다.
- 개별 수정 후 상단에 `사용자 작전`을 표시한다. 기존 프리셋 이름이 적용 중인 것처럼 남지 않게 한다.
- `리더 변경`은 이름이 있는 단일 동작으로 제공하고, 나머지 순서 변경은 별도 편집 모드에 둔다. 현재 작은 ▲▼를 리더 지정의 유일한 수단으로 두지 않는다.
- `현재 행동: 쿠키 회복 중`, `공격 스킬 대기: SP 절약` 같은 설명은 엔진이 실제 선택한 이유를 전달할 수 있을 때만 노출한다. UI가 HP만 보고 원인을 추정하지 않는다. 이유 이벤트 추가는 별도 L 작업이다.

```text
[파티]                         [사냥 보기]
[작전: 사용자]       [프리셋 선택 >]
교전 최대 [3마리]     전투 후 휴식 [20%]
[쿠키·리더] [마루·힐러] [보리·마법]
마루 | 현재 행동: {엔진의 실제 상태}
공격 대상 [협공 >]   위치 [직업 자동 >]
공격 스킬 [SP 절약 >]  힐 [HP n% 이하 >]
[자동 스킬 목록 >] [파티 공용 포션 >]
```

**완료 기준:** 파티 탭에서 힐 기준과 SP 정책을 조정할 수 있고, 전투 관찰 시 왜 공격/회복/대기를 하는지 확인 가능하다. 프리셋으로 덮어쓸 값이 적용 전에 보인다.

### 2) 패널 높이가 작업과 맞지 않고, 남겨 둔 필드도 온전히 보이지 않는다

**화면:** 모든 패널, 특히 상태·스킬·장비·카드.

**관찰:** 상태·스킬·가방·설정은 y≈302에서, 장비·카드·지도·파티·마을은 y≈140에서 시작한다. `.sheet` 60%, `.sheet.tall` 78% 두 종류다(`styles.css:173–188`, `App.tsx:25`). [equip.png](shots/equip.png)에서는 상단 필드에 쿠키 머리가 잘리고 파티 프레임도 일부만 남는다. **패널이 파티 프레임 아래쪽을 덮는 것이며, 제목이 프레임에 가려진 상황은 아니다.** 반면 [status.png](shots/status.png)는 필드에 약 260px를 남기고 스탯 목록은 INT 도중에 끊긴다. `FieldView.tsx:92–99`가 패널마다 카메라 하단 여백을 수동 계산한다.

**영향:** 관리 작업 중에는 스크롤이 늘고, 지켜보려 남긴 전투는 머리·이름표가 잘린다. 메뉴 전환마다 캐릭터 위치가 크게 달라져 공간 감각도 흔들린다.

**제안 — L:** 페이지를 세 가지 용도로 정리한다. ① 사냥은 전체 필드, ② 파티 조정은 관찰 영역을 펼칠 수 있는 관리 페이지, ③ 성장·가방·탐험은 상단 **사냥 상태 한 줄**만 남기는 관리 페이지. 현재의 60%/78% 자동 분류를 없앤다. 관리 페이지에서는 기존 파티 레일·미니맵·퀵바를 뒤에서 잘라 보이지 말고 숨긴다. 상세 아이템 등 짧은 작업만 바텀 시트로 연다.

```text
관리 페이지                    파티 관찰 펼침
+--------------------------+   +--------------------------+
| 햇살 평원 · 사냥 중   [v] |   | 햇살 평원 · 사냥 중   [^] |
| 성장                [닫기]|   | 전투 관찰: 캐릭터 전신    |
| [스탯][스킬][장비][카드]   |   | HUD 중복 없이 위험만 표시 |
| 선택한 작업의 본문         |   | 파티 설정                 |
| ... 단일 세로 스크롤 ...  |   | ...                      |
| 사냥 파티 성장 가방 탐험  |   | 사냥 파티 성장 가방 탐험  |
+--------------------------+   +--------------------------+
```

**완료 기준:** 같은 캐릭터·같은 전투 상태에서 패널을 연 뒤 핵심 인물의 머리/발이 잘리지 않는다. 360×800과 390×844에서도 제목·닫기·주 동작이 항상 접근 가능하다. 관찰 영역의 높이는 렌더러가 실제 레이아웃 측정값을 받아 결정한다.

### 3) 2배 스크린샷에서는 커 보여도 실제 조작 요소와 본문은 매우 작다

**화면:** 공통, 스킬 +, 파티 순서, 설정 스위치, 닫기.

**관찰:** `.win-title .x`는 **20×18px**, 상단 버튼은 32×28px, `.toggle`은 34×18px다(`styles.css:56,187,252`). 본문 기본은 12px, `.small`은 10px, 퀵슬롯 AUTO는 8.5px다. [skills.png](shots/skills.png)의 +와 [party.png](shots/party.png)의 순서 화살표는 작고 가까이 붙어 있다. 설정 스위치에는 인접 텍스트가 있지만 프로그램적으로 연결된 이름·선택 상태가 없다(`World.tsx:194–209`).

**영향:** 한 손 조작에서 닫기·강화·순서 변경의 오입력이 발생하기 쉽다. 중요한 선행 조건과 비용이 작은 보조 글자로 밀려 읽기 전에 눌러 보게 된다.

**제안 — M:** 이 프로젝트의 조작 목표를 **독립 터치 영역 최소 44×44px**, 본문 14px, 설명 12px 이상, 제목 16px로 잡는다. 외형 아이콘은 작게 유지해도 실제 버튼 상자는 확보한다. 서로 겹치는 투명 터치 영역으로 해결하지 않는다. 설정은 라벨을 포함한 행 전체가 하나의 토글이며, 스크롤 취소 시 실행하지 않는다.

```text
| 스킬 이름 · Lv 3/10       [상세 >] |  최소 56px 행
| 다음 효과 ...             [학습]  |  학습 버튼 44px 이상
| 효과음                 켜짐 [●]   |  행 전체 48px
| 페이지 제목                [ × ]  |  닫기 영역 44px
```

색 외에 `켜짐/꺼짐`, `선택됨`, `MAX`, `잠김` 텍스트를 둔다. 실제 `<button>`, 스위치의 접근 가능한 이름·`aria-checked`, 탭의 선택 상태, 키보드 포커스를 공통 컴포넌트로 지원한다. Galmuri를 전면 폐기하지 말고 확대된 본문에서 먼저 확인하며, 긴 설명용 일반 고딕 옵션은 비교 시안 후 결정한다.

**완료 기준:** 실제 CSS 크기로 터치 영역을 검사하고, 10자 이름·여러 줄 조건·글자 확대에서도 버튼이 겹치지 않는다. 대비는 측정 후 조정한다. 현재 화면만으로 대비 규격 위반 수치를 단정하지 않는다.

### 4) 지도는 세계를 잘 보여주지만, 무엇을 얻으러 갈지 결정하는 정보가 늦게 나온다

**화면:** 지도, 카드 도감, 아이템 정보.

**관찰:** [map.png](shots/map.png)에서 지도 그림은 y≈167–532, 약 365px를 차지한다. `wm-map`은 54%, 최소 250px다(`styles.css:501`). 맵 목록은 경험치·득템 태그까지만 보여주고, 실제 특산품은 맵 상세에 있다(`WorldMap.tsx:130–136,198–200`). 획득처가 없는 것은 아니다. 아이템 모달에 몬스터명·확률이 있지만 텍스트이고(`Modals.tsx:42,93`), 지도 상세로 이어지는 동작은 없다. 지역 핀의 `적정`은 지역 전체가 아니라 그중 레벨이 가까운 맵 하나로 계산한다(`WorldMap.tsx:88–89`).

**영향:** 목적 사냥을 하려면 도감·아이템·지도 사이의 정보를 기억해야 한다. 지역의 초록색 `적정`을 모든 하위 맵의 안전 보장으로 받아들일 수도 있다.

**제안 — M:** 처음 진입은 현재 지방의 목록에 초점을 맞추고, 세계 그림은 펼치기 가능한 개요로 유지한다. 목록에 대표 특산품 1–2개를 추가한다. 이름을 누르면 효과·드롭 몬스터·확률·등장 맵을 잇고 `이 사냥터 보기`로 해당 상세를 연다. 이동은 상세의 명시적 `이동` 버튼으로만 한다.

```text
탐험 [세계 지도 펼치기 v]
햇살 평원 지방       [목적: 전체 v]
네잎 언덕 · Lv 8~18 · 레벨 기준 쉬움
득템: {데이터의 특산품 2개}        [상세 >]
물레방아 수로 · 경험치 / 제니       [상세 >]
목표: {선택한 카드/장비}     [획득처 보기]
```

도감에서 목표 1개를 표시하는 기능을 제안한다. 목표는 드롭을 보장하지 않고, 자동 이동도 하지 않는다. `적정`은 `레벨 기준 적정`으로 바꾸며 속성·명중·선공은 별도 정보로 둔다. 미발견 장소의 이름·드롭을 새 역방향 링크로 유출하지 않도록 `zoneKnown`/봉인 규칙을 공통 적용한다.

**완료 기준:** 알려진 카드에서 해당 사냥터 상세까지 맵 이름을 외우지 않고 도달한다. 지역 핀과 하위 맵의 평가 범위를 오해하지 않는다.

### 5) 장비를 바꿀 때 파티 전체에 무엇이 달라지는지 비교하기 어렵다

**화면:** 장비, 아이템 상세, 상점.

**관찰:** [equip.png](shots/equip.png)는 인형과 10개 부위 배치가 명확하지만 전부 `—`이고 하단이 비어 있다. 부위를 누르면 후보가 나타나는 방식이다(`EquipBag.tsx:28–38,108–142`). 후보에는 기본 ATK/DEF와 착용자만 표시한다. 상점에는 기존 비교가 있으나 `upgradeScore`는 공격력·정련·일부 마법/방어 수치의 단순 점수다(`Shop.tsx:71–77`). 속성·슬롯·카드 가치를 반영하지 않은 `추천▲`가 붙을 수 있다.

**영향:** 주운 슬롯 무기와 기본 공격력이 높은 상점 무기의 교환 가치를 판단하기 어렵다. 동료 장비를 가져오는 동작도 받는 사람만 보면 파티 손실을 놓친다.

**제안 — M:** 인형 배치는 유지한다. 빈 부위에는 `미장착 · 후보 n개`를 표시하고, 최초 진입 시 무기 부위를 선택해 후보를 아래에 보여준다. 미리보기 단계에서는 세이브를 변경하지 않는다. 후보 선택 후 비교 시트를 열어 선택 캐릭터 기준 실제 장비 교체 전후 파생값과 속성·슬롯·꽂힌 카드를 함께 보여준다.

```text
쿠키 [장비] [의상]
{기존 부위 + 캐릭터 인형 배치}
무기 · 미장착                후보 n개
[후보 이름 [슬롯 수]]  {착용자/요구 조건}
---------------- 비교 시트 ----------------
현재 → 후보 | ATK / ASPD / 관련 변화
속성: ...   슬롯: ...   꽂힌 카드: ...
마루에게서 가져옴: {마루의 변경 결과}
                       [쿠키에게 장착]
```

`추천▲`는 일단 `기본 공격력↑` 같은 실제 비교 항목으로 좁힌다. 모든 장비를 단일 전투력으로 순위화하지 않는다. 두손 무기의 방패 해제와 액세서리 1/2의 교체 대상을 명시한다. 후보 없음은 해당 부위 상점 또는 **알려진** 획득처로 연결한다.

**완료 기준:** 카드/속성/방패 손실을 포함해 교체 효과를 사전에 볼 수 있다. 실제 적용 결과와 미리보기가 동일한 계산 경로를 쓴다.

### 6) 카드 첫 화면이 수집의 기대보다 빈 장비 표를 먼저 보여준다

**화면:** 카드.

**관찰:** [cards.png](shots/cards.png)의 y≈264–620은 장비 없는 부위 10행이다. `빈 슬롯 0칸` 아래 점선 상자는 실제 카드 슬롯이 아니라 미장착 아이템 자리인데 시각적으로 혼동될 수 있다(`Cards.tsx:86–103`). 기본 탭은 언제나 슬롯 관리(`:42`). 도감은 이미 지역별 카드와 미획득 확률·몬스터 상세 연결을 제공한다(`:194–217`).

**영향:** 아직 카드가 없는 플레이어는 무엇을 모을지보다 할 수 없는 작업을 먼저 본다. 카드가 있어도 슬롯 장비가 없으면 `꽂기` 불가 이유와 다음 행동을 찾아야 한다.

**제안 — M:** 명시적 선택을 기억하되 최초 방문에는 상태에 따라 진입점을 고른다. 카드 미보유·미장착이면 도감/목표, 보유 카드가 있으면 보유 목록, 꽂을 대상이 있으면 슬롯 관리를 강조한다. 10개 부위의 완전한 표는 유지하되 미장착 부위는 `미장착 부위 10개 펼치기`로 접는다.

```text
카드 [보유] [슬롯] [도감]
아직 획득한 카드가 없습니다.
{현재 사냥터의 공개 카드와 효과}
[획득처 보기]              [목표로 표시]
--------------------------------------
보유는 있음 / 호환 장비 없음:
{카드 이름} · 갑옷 카드
빈 슬롯이 있는 갑옷이 필요합니다. [찾기]
```

`장비 미착용 / 장비에 슬롯 없음 / 빈 카드 슬롯 / 장착 완료`를 글과 모양으로 구분한다. 기존의 카드·장비 양방향 선택과 제거 불가 확인은 유지한다. 첫 카드 알림은 장착 가능 여부와 별개로 남기되, 장착 권유 배지는 기존처럼 실제 가능할 때만 표시한다.

**완료 기준:** 0장 상태에서 목표 사냥으로 이어지고, 카드가 있어도 꽂을 수 없는 이유를 표 한 번 훑어서 알 수 있다.

### 7) 스킬의 만렙·포인트 부족·선행 조건 미충족이 모두 비슷한 +로 보인다

**화면:** 스킬.

**관찰:** [skills.png](shots/skills.png)에는 만렙 패시브 3개와 미학습 스킬에 모두 흐린 +가 있다. `canLearn`의 false가 하나의 disabled 버튼으로 표현된다(`StatusSkills.tsx:214–229`, `state.ts:260–266`). 선행 조건 텍스트는 있지만 설명 펼침은 아이콘/제목 클릭이라는 단서가 약하다. 전직 조건은 같은 Job 40 조건을 문장 안에서 반복한다(`StatusSkills.tsx:202`).

**영향:** 자신의 빌드를 설계하려면 각 스킬을 눌러 보며 실패 사유를 추리해야 한다. 자동 사용 토글도 학습과 같은 행에서 설명 없이 등장해 투자와 전투 정책이 섞인다.

**제안 — M:** 스킬 행의 우측을 `학습 +1 / MAX / 포인트 부족 / 선행 필요`로 구분하고, 상세 펼침 화살표를 명시한다. 비활성 학습 버튼과 별개로 상세는 항상 열리게 한다. 상세에는 현재→다음 효과, SP, 사용 조건, 필요 포인트를 표시한다. 학습 성공 시 해당 행의 레벨·잔여 포인트·새 효과가 함께 바뀐다.

```text
검사 · 스킬 포인트 0
기사 전직: Job 20 / 40          [조건 >]
한손검 수련     10/10             [MAX]
강타            0/10      [포인트 부족]
폭렬검          0/10       [선행 필요 >]
  강타 0/5                       [강타 보기]
{학습한 액티브}  자동 사용: 켜짐 [파티 설정]
```

선행 스킬 링크는 같은 화면의 해당 행으로 이동한다. 학습하지 못하는 과거 직업 스킬은 `학습 종료`로 구분한다. 장문의 전직 안내는 한 줄 진행 상태와 상세로 줄인다.

**완료 기준:** 포인트 0, MAX, 선행 미충족, 학습 가능, 이전 직업 학습 종료 상태를 색 없이도 구별한다.

### 8) 스탯 포인트 알림이 실제 행동 가능 여부와 다르고, 일괄 분배의 비용 설명이 부족하다

**화면:** 파티 레일, 상태.

**관찰:** [status.png](shots/status.png)는 잔여 1점, STR 필요 4 / AGI 3 / VIT 4 / INT 2를 보여준다. 레일은 비용과 관계없이 `statPts > 0`이면 +1을 강조하고, 그 분기가 전직 배지보다 앞선다(`Hud.tsx:83`). 스탯 한 단계 비용과 `+5/+10` 선택이 공존하지만 표시 비용은 언제나 다음 한 단계 비용이다(`StatusSkills.tsx:53–69`). `raiseStat`는 선택 수만큼 못 사면 가능한 만큼만 올리고, 추천 분배는 미리보기 없이 즉시 소비한다(`state.ts:242–250`, `StatusSkills.tsx:136`).

**영향:** 쓸 수 없는 포인트가 계속 호출하고, +10이 10포인트인지 10단계인지 애매하다. 작은 스크롤 중 `onPointerDown`으로 즉시 분배가 시작되는 것도 의도하지 않은 소비 위험이다(`StatusSkills.tsx:13–19`).

**제안 — M:** 강조 배지는 `STAT_KEYS.some(비용 충족 && 99 미만)`일 때만 켠다. 남은 점수는 상세에서 항상 보존·표시하고, 전직 가능 알림은 별도 우선순위로 둔다. 선택 단위는 `1단계 / 5단계 / 10단계`; 실제 구매 수와 총비용을 함께 보여준다. 추천 분배는 안을 먼저 표시하고 한 번 적용한다.

```text
스탯 · 보유 1점
지금 올릴 수 있는 능력치가 없습니다. 다음 성장 때 사용하세요.
[1단계] [5단계] [10단계] [추천안 보기]
STR 기본 29 + 보정 2
다음 1단계: 4점 / ATK +1      [포인트 부족]
{5단계 선택 시: 실제 n단계 · 총 p점 · 변화량}
```

탭은 pointer-up/click에서 확정하고 이동 제스처는 취소한다. 연속 올리기는 명시적 길게 누르기 지연 후 시작하며 떼기·취소·화면 이탈에서 멈춘다. 기존의 증가량 미리보기와 성공 bump는 유지한다.

**완료 기준:** 행동 불가능한 +배지가 전직을 가리지 않는다. 일괄 분배의 미리보기 단계·비용·결과가 실제 소비와 일치한다.

### 9) 필드 HUD는 고정 정보가 크고, 현재 사냥 상태와 보스 준비의 의미는 작다

**화면:** 필드.

**관찰:** [field.png](shots/field.png)의 파티 레일은 약 132px 폭, y≈48–228을 사용한다. 반대편 미니맵은 84×70px이고 보스 `0/90`은 그 아래 9px 글자다(`styles.css:69,122–124`). 지금 수치는 처치 진행이지만 단위가 없다. 게이지가 차야 소환 버튼이 등장한다(`FieldView.tsx:49–57`). 필드 헤더는 지역명·레벨·돈이며 현재 작전·휴식·탐색 여부는 표시하지 않는다. QA 화면의 조용함 자체를 문제로 삼는 것은 아니다.

**영향:** 방치 후 잠깐 보는 사용자는 전투가 잘 돌아가는지, 쉬는 중인지, 보스를 부를 수 있는지부터 알고 싶다. 레벨·직업 반복 정보가 그 판단보다 먼저 눈에 들어온다.

**제안 — M:** 필드에는 상단 가로 3인 요약을 시안으로 검증한다. 초상·이름·HP/SP를 유지하고 직업/Job/EXP 상세는 캐릭터 정보로 보낸다. 현재 상태는 `사냥 중 / 탐색 중 / 전투 후 휴식 / 부활 대기`처럼 엔진 상태로 표시한다. 미니맵은 축소/펼침 가능한 보조 정보로 둔다.

```text
햇살 평원                  50,000z [설정]
[쿠키 HP/SP] [마루 HP/SP] [보리 HP/SP]
균형 · 탐색 중                       [지도]
                 필드
보스 준비: 처치 0/90                 [정보]
{준비 완료: 뿔토끼 대장 도전 가능 [소환]}
{전투 중: 보스 이름 + HP / 준비 게이지 접힘}
```

보스 정보에서 이름·주요 보상·자동 소환 켜짐/꺼짐을 보여준다. 모든 사냥터에 보스가 있다고 가정하지 않고 현재와 같이 없는 게이지는 숨긴다. 성장 배지는 #8 규칙을 적용한다.

**완료 기준:** 위험·휴식·소환 준비 상태를 한눈에 구별하며, 3인/1인/사망/버프 다중 상태에서 전투 중심을 가리지 않는다.

### 10) 오프라인 보고는 지급 내역은 보여주지만 다음 결정을 연결하지 않는다

**화면:** 복귀 모달. 첨부 화면 없음; 코드 근거.

**관찰:** 보고에 시간·사냥터·처치·경험치·레벨 상승·카드·장비·60%/12시간 규칙이 이미 있다(`Modals.tsx:128–150`). 그러나 아이템은 클릭 동작 없는 `ItemSlot`이고 마지막 행동은 `확인` 하나다. 장비 보고는 인스턴스 UID 없이 아이템 ID 배열이다(`offline.ts:11–22,109`). 보상은 모달 확인 전에 이미 적용된다(`game.ts:55–69`). 계산은 최근 속도 기반의 추정이며 오프라인 전투 하나하나를 재생한 기록은 아니다(`offline.ts:79–89`).

**영향:** 복귀의 보상 감정이 긴 목록 확인으로 끝나고, 새 장비 비교·성장 투자·전직·사냥터 재선택으로 자연스럽게 이어지지 않는다.

**제안 — M, 정확한 신규 장비 링크/보고 보존은 L:** 희귀 획득→성장 변화→일반 획득 순서로 요약한다. `보상 반영 완료`를 명시하고 주 동작은 `계속 사냥`, 보조 동작은 조건부 `새 장비 보기 / 성장 확인`이다. 장비 UID를 보고에 담기 전에는 같은 이름의 임의 장비로 연결하지 말고 가방 필터로 이동한다.

```text
자리를 비운 동안 · {실제 부재 시간}
보상 계산 {적용 시간} / 최대 12시간 · 반영 완료
★ {새 카드/희귀 장비, 없으면 이 영역 생략}
쿠키 Lv a→b · Job c→d   [성장 확인]
{처치 / EXP / 판매 제니 / 일반 획득 펼치기}
{밤길 종료 등 실제 기록된 이동 사유}
[새 장비 보기]                  [계속 사냥]
```

현 보고에는 원래 부재 시간과 시작 레벨이 없으므로 별도 필드가 필요하다. 추가 전에는 기존의 `계산 시간`, `레벨 +n`으로 정직하게 표기한다. 마을 체류·1분 미만·획득 없음은 빈 보상 모달을 강제하지 않는다. 추정 보고에서 `힐을 32회 사용했다` 같은 미기록 전투 내역을 만들어내지 않는다. 마지막 보고는 사냥 기록에서 다시 볼 수 있게 한다.

**완료 기준:** 보고를 닫거나 새로고침해도 중복 지급되지 않고, 실제 신규 획득물과 가능한 성장 행동을 찾을 수 있다.

### 11) 중요한 사건을 놓쳤을 때 다시 찾는 경로가 약하다

**화면:** 필드 로그, 카드 획득·전직·해금·전멸 알림.

**관찰:** 일반 토스트는 2.6초, 카드 4.2초이며 동시 최대 4개다(`game.ts:140–144`). 필드 로그는 접힌 상태 최근 6개/펼친 상태 40개, 열기 버튼은 투명 영역이다(`FieldView.tsx:64–75`, `styles.css:143`). 월드 로그 자체는 최근 80개 메모리 목록이다(`world.ts:218–220`). 카드 드롭은 지급→바닥 연출→획득 배너 흐름이 이미 있다(`world.ts:1892–1922`); 연출 부재라고 평가하지 않는다.

**영향:** 자동 사냥에서 매 순간 보고 있지 않아도 중요한 득템·지도 해금은 알아야 한다. 패널을 보는 사이 지나간 배너를 놓치면 실제로 달라진 것과 다음 선택이 연결되지 않는다.

**제안 — M, 저장 기록은 L:** `기록`이라는 명시적 입구를 사냥 화면에 둔다. 일반 드롭은 묶고, 카드 최초 획득·전직 가능·새 지도·전멸/후퇴는 링크 있는 최근 사건 목록으로 남긴다. 모두에게 빨간 배지를 붙이지 않고 미확인 중요 사건 수만 표시한다.

```text
사냥 화면: [기록 · 새 소식 2]
최근 사건
★ {카드 이름} 최초 획득        [카드 보기]
↗ {지역 이름} 개방             [지도 보기]
! 파티 전멸 · {실제 손실/후퇴}  [파티 조정]
일반 획득: {종류별 합계}        [펼치기]
```

품질 가이드 적용은 **기존 사건의 전달을 완성하는 것**이다. 일반 공격/작은 회복은 국소 반응, 스킬 사용은 주체·대상·자원 변화, 보스 종료는 사망→보상→결과, 신규 카드에는 더 강한 첫 획득 강조를 준다. 실제 동작 영상 확인 전에는 타격 지연이나 연출 과다를 확정하지 않는다. 기록 클릭은 조회·이동만 하며 보상을 다시 지급하지 않는다. 감소된 모션에서도 텍스트·결과는 남긴다.

**완료 기준:** 관리 화면을 연 채 카드 획득과 해금이 일어나도 나중에 출처와 결과를 다시 확인할 수 있다.

### 12) 퀵슬롯은 수동 사용·길게 눌러 설정·작은 AUTO 토글이 한곳에 겹쳐 있다

**화면:** 필드, 퀵슬롯 설정.

**관찰:** [field.png](shots/field.png)에는 포션 1개와 빈칸 4개가 동일한 크기로 배치되어 있다. 채워진 슬롯은 짧게 누르면 즉시 사용, 450ms 길게 누르면 설정, 작은 AUTO 표시는 별도 pointer-up 토글이다(`QuickBar.tsx:46–77`). `HP40%`는 필드에서 대상과 임계 조건을 설명하지 않는다. 상세에는 파티 최저 비율 대상과 슬롯 우선순위 설명이 이미 있다(`:137–139`). 다만 상세의 `이하` 문구(`:134`)와 `world.ts`의 `autoItems()` 내 `r * 100 < q[i].pct` 판정은 다르다. 바 폭은 고정 요소 합계 약 335px여서 320px 화면에서는 넘칠 것으로 예상된다(`styles.css:386–430`); 이 폭은 실기기 재현 필요다.

**영향:** 자동 사용을 켜려다 수동으로 소비하거나, 켜진 줄 알고 방치할 수 있다. 비상 소비 도구의 상태가 작고 모호하면 사냥 결과를 신뢰하기 어렵다.

**제안 — M:** 슬롯 본체의 수동 사용은 유지하되 필드의 작은 AUTO 토글은 상태 표시로만 사용한다. `편집`을 명시적 44px 버튼으로 제공하고 긴 누르기는 보조 진입으로 남긴다. 편집에서 5칸 모두 보이게 하며, 필드에서는 등록 슬롯과 `+ 등록` 하나를 보여 공간을 회수한다. 슬롯 번호·우선순위는 유지한다.

```text
필드: [포션 99] [등록+]                 [편집]
      자동 · HP<40%
설정: [1][2][3][4][5]
사용 대기시간이 끝난 생존 동료 중 HP 비율 최저
HP [40%] 미만일 때      자동 사용 [켜짐]
{수량 0: 품절 · 자동 사용 대기}       [상점]
```

실제 엔진 대상 규칙과 문구를 일치시킨다. 자동 대기/수동/버프 유지 중/품절을 구분하고, 사용 결과는 수혜자와 감소 수량을 짧게 보여준다. 패널 안에서도 파티→공용 포션으로 접근 가능하게 한다.

**완료 기준:** 설정 열기·스크롤 취소가 포션 소비로 이어지지 않는다. 1개/5개 등록, 품절, 버프, 320px 폭에서 조작 가능하다.

### 13) 가방은 아이콘 보관함으로는 충분하지만 획득물 검토 도구로는 부족하다

**화면:** 가방.

**관찰:** [bag.png](shots/bag.png)는 장비 2개가 이름 없는 아이콘으로 보인다. `ItemSlot`에는 정련·슬롯·E·수량은 있지만 이름은 title 속성뿐이다(`widgets.tsx:139–149`). 기본 목록은 착용 여부/부위/가격 순서이며 신규 획득 순서나 캐릭터 적합 필터가 없다(`EquipBag.tsx:157–170`). 빈 공간은 QA 수량 때문이지 버그가 아니다.

**영향:** 사냥을 오래 돌린 뒤 비슷한 장비를 하나씩 열어야 비교가 가능하다. 모바일에는 hover 이름표가 실질적 안내가 되지 않는다.

**제안 — M:** 기본을 이름 있는 목록으로 하되 기존 격자 모드를 유지하고 선택을 기억한다. `최근 획득 / 부위 / 이름` 정렬, `쿠키 착용 가능`, `슬롯 있음` 필터를 제공한다. 최근 획득 정렬에는 실제 획득 순서 데이터가 필요하며 가격 순서를 최근처럼 표시하지 않는다.

```text
가방 · 파티 공용        [목록 | 격자]
[장비 2] [소비 1종] [기타] [카드]
[최근 획득 v] [쿠키 착용 가능] [슬롯 있음]
[그림] {장비명 [슬롯]} · +정련
       {소유자 / 착용 조건}        [비교]
```

개수와 종류 수를 구분한다(현재 소비 1은 99개 포션 1종일 수 있음). 장비가 없는 때만 상점/획득처 행동을 제공하고, 매 화면을 안내문으로 채우지 않는다. 판매는 검토 동작과 분리하며 장착 중·카드 삽입 장비를 일괄 처리에 자동 포함하지 않는다.

**완료 기준:** 2개 상태와 100개 상태 모두 이름·슬롯·정련·착용자를 모달 없이 훑을 수 있다. 신규 획득물의 비교까지 짧게 이어진다.

### 14) 첫 세션 안내가 시간 기반 토스트여서 필요한 순간 전에 사라진다

**화면:** 첫 필드, 첫 장비·스킬·동료 해금. 첨부 QA 화면으로 신규 진행은 확인 불가.

**관찰:** 시작 600ms 뒤 자동 사냥/집중 공격 안내, 4.5초 뒤 Job 10/기본기 9 안내를 띄운다(`App.tsx:115–119`). 토스트는 곧 사라진다. 동료 해금 때는 알림과 레일 입구가 이미 있다(`world.ts:1874–1875`, `Hud.tsx:88–89`). 신규 게임은 시작 스탯을 자동 분배한다(`App.tsx:110–112`).

**영향:** 초반에 미래 규칙을 암기해야 하고, 실제 선택 시점에는 배운 내용을 찾기 어렵다. 전투를 수동으로 계속 조작해야 한다고 오해할 수도 있다.

**제안 — M:** 시간 대신 실제 상태로 여는 비강제 안내를 둔다. 첫 사냥은 `자동으로 사냥합니다. 몬스터를 누르면 집중 공격합니다.` 한 줄만 남기고, 첫 착용 가능한 장비·학습 가능 포인트·동료 슬롯·전직 조건에서 각각 한 번 안내한다. 보상 지급이나 강제 자동 장착으로 튜토리얼을 대체하지 않는다.

```text
사냥 도움말                          [닫기]
첫 장비를 얻었습니다. {캐릭터}와 비교해 보세요.
[장비 비교]                          [나중에]
```

한 번에 안내 하나만 노출하고, 나중에 선택은 도움말/성장 화면에 남긴다. 조건 충족과 실제 완료를 구분하여 새로고침 후 안내가 반복되지 않게 한다. 첫 동료 영입 후에는 `직업에 맞춰 싸웁니다 → 파티 작전 보기`를 연결한다. 시작 자동 스탯 분배는 결과를 알려주되 이번 UX 개편에서 임의 제거하지 않는다.

**완료 기준:** 시작 5초간 화면을 보지 않아도 첫 장비·스킬·전직 행동을 이후에 찾을 수 있다. 해금 전 기능을 강제로 체험시키지 않는다.

### 15) 마을은 서비스인지 이동인지 혼동될 수 있고, 사냥 정책이 일반 설정에 섞여 있다

**화면:** 마을, 설정.

**관찰:** [town.png](shots/town.png)는 상단 지역은 햇살 평원인데 내부 배너가 미드가르 성이며 하단 탭은 `마을`이다. 원격 서비스 설명은 있지만 실제 휴식 이동 경로는 맨 아래 긴 안내에 있다(`World.tsx:161–178`). [settings.png](shots/settings.png)에서는 잡템 자동 판매·보스 자동 소환이 음향/표시 옵션과 같은 화면이다(`World.tsx:205–209`). 초기화 확인창과 브라우저 저장 안내는 이미 있으므로 부재로 보지 않는다(`:223–225`).

**영향:** 서비스 창을 열었으니 안전 지대에 있다고 생각할 수 있고, 보스 도전 정책을 바꾸려면 기기 설정 같은 화면을 찾아야 한다. 한 손으로 재정비하는 목적과 메뉴 이름이 어긋난다.

**제안 — M:** 탐험 안에 `지도 / 마을 서비스`를 두고 서비스 제목에 `사냥 계속 중`을 표시한다. NPC 6개 카드는 유지한다. 상단에 `성으로 이동해 휴식`이라는 명시적 동작을 둔다. 지도에서 실제 마을로 이동하는 기존 규칙을 재사용하고, 서비스 열기와 이동은 다른 동작으로 유지한다.

```text
탐험 [지도] [마을 서비스]
마을 서비스 · 햇살 평원에서 사냥 계속 중
[성으로 이동해 휴식]
{기존 NPC 2열 카드}

설정: [소리] [표시·모션] [저장·기록]
자동 판매 → 가방 기타 탭의 같은 설정
자동 보스 → 사냥 보스 정보 / 파티 공용 정책
```

일반 설정에는 각 정책으로 가는 링크만 남겨 기존 사용자의 경로를 보존한다. `이펙트 간소화`와 `모션 줄이기`는 서로 목적이 다르므로 후자는 별도 지원 범위를 정한다. 현재 reduced-motion은 버프 깜빡임 한 규칙만 제어한다(`styles.css:873`).

**완료 기준:** 마을 서비스 이용 중 사냥이 계속된다는 것을 확인할 수 있다. 자동 보스와 자동 판매를 실제 관련 화면에서 찾아 바꿀 수 있으며 서로 같은 저장값을 사용한다.

## 2. 구조 권고: 결정할 기본안

### 탐색 구조

**하단 5개: 사냥 / 파티 / 성장 / 가방 / 탐험.** 다음을 최종 기본안으로 제안한다. 현재 6개 탭에서 카드만 없애는 축소안이 아니라, 캐릭터 단위 결정과 파티 단위 결정을 묶는 안이다.

| 주 메뉴 | 내부 구성 | 보존할 빠른 경로 |
|---|---|---|
| 사냥 | 필드, 포션, 보스, 최근 사건 | 초상→그 캐릭터 성장, 목표 아이템→획득처 |
| 파티 | 작전, 파티원 AI, 공용 소비/소환 정책 | 힐 기준·스킬 자동 사용, 관찰 펼치기 |
| 성장 | 스탯 / 스킬 / 장비 / 카드, 공통 캐릭터 선택 | 카드 획득 알림→보유 카드, 빈 장비→후보 |
| 가방 | 장비 / 소비 / 기타 / 카드 바로가기 | 카드 목록은 동일 카드 관리 화면으로 연결 |
| 탐험 | 지도 / 마을 서비스 | 지역명→지도, 포션 품절→도구 상점 |

카드 도감과 보유량은 파티 공용이고 장착 대상만 캐릭터별이다. 카드 내부에서 도감/보유를 볼 때 캐릭터 선택을 필수로 요구하지 않는다. 카드를 성장 안으로 옮겨 발견성이 낮아질 위험은 **카드 탭 명시, 최초 획득 기록, 목표 사냥 바로가기**로 보완한다. 그래도 카드 접근이 악화되면 다음 라운드에서 별도 주 메뉴 유지안과 실제 과업 횟수를 비교할 필요가 있다.

메뉴는 다시 눌러도 닫히지 않는 일반 페이지 방식으로 통일한다. 사냥 탭 또는 제목의 닫기로 필드에 복귀한다. 현재 `openPanel`의 같은 메뉴 재선택 토글(`game.ts:156–160`)은 새 주 메뉴에 적용하지 않는다.

### 높이·스크롤·뒤로가기 계약

- 화면 전체 높이는 100dvh, 하단 내비는 **콘텐츠 높이 + safe-area**로 계산한다. 현재처럼 고정 58px 안에 safe-area padding을 넣는 방식과 시트의 별도 margin을 새 구조에서 함께 점검한다.
- 관리 페이지는 상단 사냥 상태 44px, 제목 48px, 나머지 본문을 기본으로 한다. 파티 관찰은 펼칠 때 약 160–200px를 시작값으로 시험하되 짧은 화면에서 접을 수 있게 한다. 필드를 강제로 작은 띠에 그리지 않는다.
- 주 페이지별 본문은 세로 스크롤 하나. 제목·캐릭터 선택·필수 적용 동작은 고정하고, 도움말·장문의 계산 결과는 본문에 둔다. 지도도 큰 고정 그림과 짧은 독립 스크롤 목록의 조합을 피한다.
- 카드/장비/몬스터 상세는 한 단계씩 뒤로 갈 수 있는 상세 스택을 쓴다. 현재 단일 `modal` 교체(`game.ts:17–28,171`)는 몬스터→드롭 아이템 이동 시 앞 모달로 돌아가는 상태를 담지 못한다.
- 최소 보존 상태: 주 메뉴, 내부 탭, 캐릭터 **ID**, 선택 장비 UID, 지도 지방/맵, 필터, 스크롤 위치. 파티 순서 변경 후에도 같은 캐릭터를 가리켜야 한다.
- 뒤로가기 순서: 확인/상세 닫기→상위 상세→주 페이지→사냥. 모달이 열리면 하단·배경 필드 입력을 막고 포커스를 모달 안에 유지한다. 닫으면 호출 버튼으로 돌려준다. 단순 조회에 추가 확인창을 요구하지 않는다.
- 메뉴를 보는 동안 사냥은 현재처럼 계속한다. 이 정책을 상단 상태로 알리고 전멸·희귀 획득·해금은 사건 기록에 남긴다. UI 개편만으로 전투 일시정지 규칙을 바꾸지 않는다.

### 정보 우선순위와 이벤트 전달

| 상황 | 가장 먼저 보일 것 | 접을 정보 |
|---|---|---|
| 평상시 사냥 | 파티 생존, 현재 행동, 사용 가능한 포션 | 직업 레벨 반복, 상세 버프, 일반 드롭 |
| 보스 도전 | 대상·준비 여부·자동 소환 정책·전투 HP | 일반 보스 준비 게이지, 장식 알림 |
| 성장 투자 | 선택 캐릭터, 비용, 적용 전후 변화 | 전투 전체 화면, 파생 스탯 전문 |
| 장비 교체 | 슬롯·카드·속성·착용자·교체 결과 | 가격 위주의 추천 순위 |
| 복귀 | 새 희귀 획득, 성장/해금, 현재 사냥 상태 | 일반 드롭의 개별 발생 기록 |

전투와 보상 피드백은 품질 가이드의 여섯 단계를 실제 사건별로 점검한다. 입력이 없는 자동 행동도 주체의 준비 단서가 있어야 한다. 그러나 모든 단계마다 새 팝업이나 지연을 추가할 필요는 없다.

| 사건 | 접수·준비 | 실행·접촉 | 결과·정착 |
|---|---|---|---|
| 스탯 투자 | 선택 단계와 총비용 | 버튼 반응, 확정 1회 | 잔여점/능력치/변화량이 함께 갱신 |
| 힐·보호 | 시전자·대상 표시 | 실제 판정과 HP/보호 변화 연결 | 수혜자 회복 확인, 자동 사냥 지속 |
| 카드 획득 | 기존 드롭 단서 | 기존 획득 연출 | 배너→기록→도감/장착 경로 |
| 장비 교체 | 대상·교체 손익 | 명시적 장착 | 캐릭터 외형/스탯/동료 상태 갱신 |
| 보스 종료 | 마지막 공격 주체 | 사망이 읽히는 구간 | 보상→해금 기록, 반복 시 강조 절제 |

새 기록/이유 데이터는 전투 엔진의 결과를 소비해야 한다. UI에서 피해·보상·AI 결정을 다시 계산해 사실인 것처럼 설명하지 않는다. 보상의 즉시 확정과 시각 연출 분리는 현재 구현의 좋은 원칙이므로 보존한다.

### 첫 세션과 복귀의 최소 흐름

```text
첫 세션
캐릭터 생성 → 자동 사냥 확인 → 첫 장비 비교
→ 학습 가능한 스킬 → 첫 동료 영입 → 직업별 파티 작전
→ 전직 조건 충족 시 안내
  (모두 실제 발생 순서에 반응, 강제 대기/클릭 과제 없음)

복귀
이미 반영된 계산 결과 → 희귀 획득 / 성장 확인
→ [계속 사냥] 또는 [신규 장비·성장으로 이동]
→ 보고는 최근 기록에서 다시 확인
```

## 3. 바꾸지 말아야 할 것

1. **세계와 수집 구조.** 지방→개별 맵, 특산품, 속성 차이, 보스 해금, 숨겨진 장소의 순차 단서를 유지한다. 가장 높은 레벨 맵으로 보내는 자동 진행이나 최고 효율 한 곳 추천으로 평준화하지 않는다.
2. **RO식 빌드 결정.** STR/AGI 등 분리된 스탯, 스킬 선행 조건, 무기 슬롯·카드·액세서리 2칸, 의상과 능력 장비의 구분은 복잡해서 없앨 대상이 아니다. 복잡한 선택의 근거를 먼저 보여준다.
3. **파티의 직업별 성격.** 기존 균형·집중 공격·각자 사냥·안전 제일 프리셋과 개별 전술을 유지한다. 모두 같은 적을 같은 거리에서 때리게 만드는 단순화는 피한다.
4. **필드 캐릭터·환경·마을 NPC의 친근한 분위기.** 캐릭터 전신, 초상, 마을의 2열 NPC 카드, 푸른 창틀/밝은 종이 배경은 정체성이다. 모바일 대응을 이유로 무채색 운영 대시보드처럼 만들지 않는다.
5. **월드맵의 그림과 위치감.** 항상 크게 고정할 필요는 없지만 목록만 남겨 세계 지도를 없애지 않는다. 현재 위치·잠금·지방 구분은 유용하다.
6. **이미 있는 좋은 의사결정 보조.** 스탯 미리보기와 증가 피드백, 스킬 선행 문구, 장비 정련/슬롯 표시, 몬스터 약점·드롭률, 카드 효과 합계와 양방향 삽입, 상점의 목록/격자 선택을 재사용한다.
7. **의미 있는 확인과 절제된 알림.** 카드 삽입의 제거 불가 확인, 위험 정련의 장비/카드 소멸 안내, 초기화 확인은 유지한다. 평범한 메뉴 이동까지 확인창을 늘리지 않는다. 현재 카드 장착 가능성에 근거한 배지 규칙도 보존한다.
8. **수동 선택과 자동 실행의 분담.** 사냥은 자동, 목적지·빌드·전술·소비 기준은 플레이어의 선택으로 남긴다. 일괄 최고 장비 장착, 자동 스킬 투자, 무조건 상위 맵 이동을 기본값으로 추가하지 않는다.

## 4. 구현 순서와 다음 라운드 검수

우선순위 순위와 구현 순서는 다르다. 구조 의존성을 먼저 합의해야 같은 화면을 두 번 고치지 않는다.

| 묶음 | 범위 | 확인할 대표 과업 |
|---|---|---|
| A: 공통 틀 | #2·#3, #1의 주 메뉴, 상세 뒤로가기 | 3인 파티에서 스탯→장비→카드→필드 복귀, 작은 화면 터치 |
| B: 파티와 성장 | #1·#7·#8·#9·#12 | 힐 기준 변경, 작전 비교 적용, 포션 품절, 포인트 부족/전직 준비 |
| C: 사냥 목적과 획득물 | #4·#5·#6·#13·#15 | 카드 목표→공개 획득처→사냥터, 슬롯 무기 비교, 동료 장비 이동 |
| D: 세션 연결 | #10·#11·#14 | 오프라인 복귀, 희귀 획득 재조회, 첫 동료·첫 전직 |

큰 구조 합의 전에도 #3 버튼 크기, #7 상태 문구, #8 행동 불가능 배지는 국소 수정 후보다. AI 이유 이벤트·신규 장비 UID 보고·사건 저장은 UI 재배치와 구분해 공수를 잡는다.

검수는 같은 QA 데이터를 유지한 500×900 비교와 실제 목표 폭 360×800 / 390×844에서 진행한다. 320px는 축소 지원 범위를 정하기 위한 경계 검사로 둔다. 텍스트 확대와 safe-area가 있는 화면도 확인한다.

- **정상·불가 상태:** 스킬 포인트 0/MAX/선행 부족, 스탯 1점/다단계 부분 구매, 장비 없음/호환 없음/동료 착용/슬롯 없음, 카드 0장/보유/삽입 완료, 포션 품절을 각각 재현한다.
- **사용성:** 플레이어가 “왜 힐하지 않는가”, “이 장비로 무엇을 잃는가”, “이 카드를 어디서 얻는가”를 화면만 보고 설명할 수 있는지 본다. 과업당 되돌아가기와 오입력을 변경 전후 비교한다.
- **전투 관찰:** 평상시·휴식·강타 준비·보스 종료·전멸/후퇴를 짧은 영상으로 기록한다. 정지 화면으로 판정/연출 동기화를 통과 처리하지 않는다.
- **지속성:** 패널을 연 상태의 희귀 획득, 복귀 보고 도중 새로고침, 상세에서 탭 전환, 파티 순서 변경 후 선택 캐릭터, 저장 복원 시 신규 안내 재등장을 확인한다.
- **신규/실제 플레이 분리:** QA의 빈 카드·미착용 상태는 빈 상태 검수에 쓰고, 기본 신규 게임과 보유품이 많은 저장본으로 정상 흐름을 별도 확인한다.

## 5. Claude에게 묻고 싶은 것

1. **파티 AI의 이유를 엔진에서 어느 수준까지 안정적으로 얻을 수 있는가?** 행동 상태만 노출하는 1차와 “SP 절약/힐 우선/사거리” 이유 이벤트를 추가하는 2차를 나누는 편이 좋다고 본다. 현재 코드의 실제 분기와 유지 비용 관점 의견이 필요하다.
2. **메뉴 작업 중 필드를 반드시 계속 보여주어야 하는 이유가 있는가?** 나는 상태 한 줄과 선택적 관찰을 기본으로 제안한다. 레트로 감성 때문에 항상 노출해야 한다면 캐릭터가 잘리지 않는 최소 높이와 관리 작업 손실을 실제 기기에서 비교하자.
3. **카드를 성장 내부로 옮기는 것이 수집의 중요도를 낮추는가?** 내 안에서는 도감 탭·목표·획득 기록으로 강화하지만, 실제 카드 과업 빈도가 높으면 카드 주 메뉴 유지가 나을 수 있다. 현재 6개를 관성적으로 유지하는 대신 접근 횟수로 판단하고 싶다.
4. **회복·공격 스킬 정책의 우선순위는 현재 어디서 다르게 작동하는가?** 파티의 SP 절약 설명과 힐 기준·자동 사용 OFF·카드 부여 스킬의 조합을 엔진과 맞춰야 한다. 존재하지 않는 이유를 UI가 설명하면 더 나빠진다.
5. **추천 장비를 단일 점수로 계속 표기할 의도가 있는가?** 나는 속성·카드·슬롯이 중요한 게임에서는 항목별 변화가 적합하다고 본다. 기존 상점 비교를 공통 장비 비교로 확장할 때 두손 무기와 액세서리 선택의 계산 경로를 어디에 둘지 논의가 필요하다.
6. **미발견 정보의 공개 범위는 어디까지인가?** 현재 도감은 `ZONES`의 몬스터를 나열하고 지도는 `zoneKnown`으로 단계적으로 공개한다. 이 차이가 의도인지, 도감의 이름/확률도 발견 정책에 맞춰 가려야 하는지 결정해야 한다.
7. **스탯 추천 분배와 다단계 부분 구매는 의도된 계약인가?** 유지하면서 실제 구매량/총비용을 명확히 하는 안을 제안했지만, 매번 가능한 최대만 사는 방식과 선택 단계 전체가 가능할 때만 사는 방식 중 선호를 확인하고 싶다.
8. **오프라인 보고 데이터 확장의 허용 범위는?** 실제 부재 시간, 시작/종료 레벨, 획득 장비 UID, 계산 구간별 사냥터를 담으면 오해가 줄어든다. 저장 스키마 비용 때문에 어렵다면 1차에서는 현재 데이터로 정직한 요약과 가방 연결까지만 하자.
9. **목표 휴대폰의 최소 폭과 폰트 정책은?** 500px QA만으로 실제 가독성을 판단하기 어렵다. 360/390px를 우선 제안하며 픽셀 글꼴 확대와 긴 설명용 고딕을 나란히 비교하고 싶다.
10. **실제 플레이에서 보스 실패·휴식·포션 부족이 어느 정도 발생하는가?** 이번 조용한 QA 화면만으로 경고의 강도·빈도를 정할 수 없다. 기본 신규 플레이와 중반 파티의 짧은 영상을 다음 라운드 근거로 삼자.

이번 라운드의 변경은 이 검토 문서 하나다. 코드·자산·게임 규칙은 수정하지 않았고, 위 설계의 실제 조작성과 전투 체감은 구현 후 검수 대상으로 남긴다.
